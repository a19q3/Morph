## Verdict

The implementation is broadly aligned with the paper at the *level of intent* but is materially drifted from the *letter* of the paper at the wire-format, struct-shape, and field-name boundaries. The most consequential drifts are:

1. **Conservation invariants cross paper boundary in the wrong direction.** The paper defines the bilateral `StateHeader.phase` enum with five members, but `Phase` in `morph-core/src/types.rs:16-21` is a 4-variant enum; the paper's `factory_active` is not a `StateHeader.phase` value in the implementation. The `partition_conservation` body in `validation.rs:894-963` matches the paper's general shape, but the State Cell type pseudo-code at `paper.tex:890,919,949,966` invokes four operation-specific helpers (`partition_conservation_for_publication`, `_for_close`, `_for_materialisation`, `splice_partition_conservation`) that are **not defined in the paper and not implemented in the code**. The implementation has only the generic predicate, called as `validate_partition_conservation(&ctx.partition, &ctx.asset_registry)` (no `op` parameter even though the paper's body takes one).
2. **The signed message domain string differs.** The paper's `m_n = H("CKB_MORPH_CHANNEL_STATE_V1" || canonical(Header_n))` at `paper.tex:638-640` is a different bytes string from `b"CKB_MORPH_CHANNEL_STATE"` used in `morph-core/src/hash.rs:9` and `morph-script-common/src/lib.rs:139`. The on-chain signing digest does **not match** the paper's specification.
3. **The canonical `funding_anchor_identity` digest is not implemented.** The paper's `H("CKB_MORPH_FUNDING_ANCHOR_V1" || channel_id || funding_epoch || fund_cell_type_hash || fund_cell_type_args || vault_set_commitment)` formula at `paper.tex:312-319` is absent from the implementation; the StateHeader carries a 32-byte `funding_anchor` field that is set directly by the State type script (Type-ID-style profile at `morph-state-type/src/main.rs:177-189`) and matched against script args, with no digest input from the StateHeader fields at all. The `funding_anchor_derivation_matches` predicate at `paper.tex:862` is not implemented; the type script only checks `new_header.funding_anchor() == expected_funding_anchor` (script args).

I have not duplicated S1–S5 from `MORPH_INTERNAL_AUDIT_2026-06-21.md`. Where the audit-response or patch doc fixes drift that overlaps with W2 findings, I note it explicitly. The patch doc (`MORPH_PATCH_2026-06-22.md`) is a *plan*, not an applied edit, so all paper-side findings below still hold against the working tree.

## C. 概念不一致 (Conceptual Mismatches)

### C.1 `TerminalReceipt` — paper-only

The paper defines `TerminalReceipt` as an "admissible only for descriptor-authorised remaining vault spends in profiles that explicitly allow non-atomic finalisation" (`paper.tex:541-558`) and the COOPERATIVE_CLOSE pseudo-code admits `exactly_one_terminal_receipt_cell(tx, channel_id)` at `paper.tex:912`. The implementation has no `TerminalReceipt` type, no witness kind, no factory envelope that produces one, and no State type branch that verifies one. `morph-state-type/src/main.rs:60-77` only dispatches on four `(input-data?, output-data?)` shapes, none of which corresponds to a terminal-receipt output. The audit-response disposition (`audit-response-2026-06-20.md`) and the prior audit's S1 both acknowledge this. The most recent `paper-implementation-audit.md:23` documents "Implementation docs state that this profile is atomic and does not create terminal receipt Cells". The drift is *intentional* but the paper's COOPERATIVE_CLOSE branch still uses the `exactly_one_terminal_receipt_cell` syntax, which has no implementation referent. **Resolution: either paper annotates the COOPERATIVE_CLOSE branch as reserved-for-non-atomic-profiles, or the implementation adds a state-type branch. The S1 patch in `MORPH_PATCH_2026-06-22.md:23-58` patches only the narrative; it does not change the COOPERATIVE_CLOSE pseudo-code.**

### C.2 `FundingContextId` — partially aligned, structurally drifted

The paper's 4-field binding at `paper.tex:354-369` is `(chain_id, channel_id, funding_anchor_identity, vault_set_commitment)` and the digest is `H("CKB_MORPH_FUNDING_CONTEXT" || chain_id || channel_id || funding_anchor_identity || vault_set_commitment)`. The Rust implementation (`morph-core/src/hash.rs:48-61`, `morph-script-common/src/lib.rs:3733-3746`) uses the **same** field set and the **same** domain string, so the digest bytes match. The structural drift is in the *meaning* of `funding_anchor`: in the paper's Type-ID-style profile, `funding_anchor_identity` is `H("CKB_MORPH_FUNDING_ANCHOR_V1" || ...)` and is a derived digest (paper 312–319), but the implementation's `funding_anchor` is the Type-ID digest `H(first_funding_input || output_index)` directly, with **no** `CKB_MORPH_FUNDING_ANCHOR_V1` domain separator (`morph-state-type/src/main.rs:184` is `blake2b256([input, index])` with no domain). The funding_context_id is therefore *correctly* derived from a Type-ID `funding_anchor`, but the *Type-ID `funding_anchor`* is itself not the canonical `funding_anchor_identity` the paper defines. A reader following the paper to a non-Type-ID deployment would compute a different `funding_anchor`, hence a different `funding_context_id`. This is documented in the paper at 343–349 but is a real interoperability risk.

### C.3 `SettlementDescriptor` — paper generic, code two-concrete

The paper declares a generic `SettlementDescriptor` struct with seven fields including `reserve_refund_policy`, `carrier_refund_policy`, `sponsor_change_policy` (`paper.tex:1749-1757`) and a `DescriptorOutput` with eight fields including `role`, `allowed_operations`, `data_commitment`. The implementation uses **two** versioned concrete descriptors (`BilateralCkbSettlementDescriptor` and `BilateralCkbXudtSettlementDescriptor`, `morph-script-common/src/lib.rs` and `schemas/morph.mol:435-456`) that carry only `version, output_count[, asset_count, xudt_type_hash], output_0[, output_1]`. The `output_n` struct has only `lock_hash, capacity[, xudt_amount]`. The `reserve_refund_policy`, `carrier_refund_policy`, `sponsor_change_policy`, `role`, `allowed_operations`, and `data_commitment` fields from the paper are **not implemented anywhere**. The factory exit verification (`morph-factory-type/src/main.rs:262-316`) only checks `capacity`, `type_hash`, and (for xUDT) `data length` and `amount`. The paper's design point — descriptors as a "narrow application runtime" with bounded policies — is implemented as a narrow *output-shape* descriptor, not a narrow *policy* descriptor. This is consistent with the paper's note that "the current bilateral profile uses fixed two-output CKB and CKB+xUDT families" (paper 1770–1772), but the struct shape in the paper is misleading to a reader who expects to find `reserve_refund_policy` somewhere on the wire.

### C.4 `Phase` enum — 5 members in paper, 4 in code (drift + drift)

The paper's `Phase = {funding, active, settling, closed, factory_active}` (`paper.tex:1186-1193`) is a 5-member set used in the phase-transition table at `paper.tex:833-846` where `factory-active` is the input phase for `MATERIALIZE`. The Rust `Phase` enum (`morph-core/src/types.rs:16-21`) has only `Funding, Active, Settling, Closed` — 4 members, no `FactoryActive` variant. The `as_u8()` mapping (`morph-core/src/hash.rs:224-233`) covers 0..=3. The wire encoding `morph-script-common/src/lib.rs:104-105, 311-313` uses `PHASE_ACTIVE = 1, PHASE_SETTLING = 2` and no factory_active value. The factory exits create a *bilateral* `StateHeader` with `phase = active` (`morph-factory-type/src/main.rs:235` checks `exit_header.phase() != PHASE_ACTIVE`) — the resulting child State Cell is `BilateralPlain` mode, not `FactoryProof` mode. The `FactoryStateHeader` (`morph-script-common/src/lib.rs:474-528`) does **not** carry a `phase` field at all; its lifecycle is `update_number`. The paper's `factory_active` phase is therefore not represented as a `Phase` value; the factory profile uses `FactoryStateHeader.update_number` for progression. The drift is consistent with the paper's later admission that "The `factory_active` phase must be paired with an explicit factory-side challenge window" (`paper.tex:2372-2375`, item F9 of the Factory Acceptance Agenda) — i.e. the phase exists in concept but is *not* a `StateHeader.phase` value in the conservative implementation.

### C.5 Factory reduced-proof names — paper vs wire

The paper's Table 12 ("Positive factory acceptance families", `paper.tex:2017-2037`) names: "Reduced rights", "CKB reduced exit", "Typed reduced exit", "Conservative factory splice", "Reduced factory splice", "Sponsored factory publication", "Recovery continuity". The implementation's 7 factory envelope kinds are: `FactorySignature`, `FactoryReducedRights`, `FactoryMerkleUpdate`, `FactoryReducedExit`, `FactoryLocalExit`, `FactorySplice`, `FactoryReducedSplice` (`morph-script-common/src/lib.rs:131-138`). The mapping is:

- "Reduced rights" → `FactoryReducedRights`
- "CKB reduced exit" → `FactoryReducedExit` (the CKB case) and the separate CKB-xUDT case
- "Typed reduced exit" → `FactoryReducedExit` with the XUDT witness (separate `FACTORY_REDUCED_EXIT_XUDT_WITNESS_LEN` constant)
- "Conservative factory splice" → `FactorySplice`
- "Reduced factory splice" → `FactoryReducedSplice`
- "Sparse single-right update" (paper Table 12 line 2) → `FactoryMerkleUpdate`
- "Local child-channel materialisation" / "Factory local exit" (paper Table 12 line 1) → `FactoryLocalExit`

The names are not a 1:1 match: paper's "Reduced rights" is generic; implementation has `FactoryReducedRights` (full state) + `FactoryMerkleUpdate` (single right) which the paper calls "sparse single-right update". The paper does not name a `MerkleUpdate` family; it bundles sparse single-right updates into "Reduced rights". A reader cross-referencing paper Table 12 with `morph-script-common/src/lib.rs:131-138` will not find a one-to-one mapping. The drift is documented in `paper-implementation-audit.md:31-32` as "strongly aligned" — but the label alignment is a stretch.

### W2-01 — Signed-message domain string lacks `_V1` suffix (HIGH)
**Severity**: HIGH
**Surface**: `paper.tex:638-640` ↔ `morph-core/src/hash.rs:9, 87-91` ↔ `morph-script-common/src/lib.rs:139, 343-345`

The state-input/output index pointers do not exist; the factory type script derives the state input/output from `Source::GroupInput/GroupOutput` directly (`morph-factory-type/src/main.rs:62-77`).
**Impact**: The paper's narrative at `paper.tex:714-756` says the envelope "names the operation, locates the authoritative State input or output, and commits to the operation body" — but the wire `kind` is a factory-witness family (1..=7), not a `ChannelOperation` tag. The script-level `classify_channel_operation(tx)` from the paper (`paper.tex:711`) is not a function in code; the operation tag is recovered from the envelope's `kind` plus the script's source-cell traversal.
**Suggested fix**: paper — rename `channel_operation` to `factory_witness_kind` in the struct definition, or add a `channel_operation` byte that takes values from the paper's 7-operation enum (`FUND..=MATERIALIZE`); the implementation would then need a new field. The current arrangement means the factory witness envelope is a *factory* envelope, not a *channel* envelope — the paper's name is misleading.

### W2-08 — `CKB_MORPH_FACTORY_BODY_V1` paper string replaced by `CKB_MORPH_WITNESS_ENVELOPE_BODY` and missing `magic, version, flags, body_len` inputs (MEDIUM)
**Severity**: MEDIUM
**Surface**: `paper.tex:1833-1846` ↔ `morph-script-common/src/lib.rs:422-429, 363-425`
**Confidence**: high
**Claim**: The paper's body-commitment formula `H("CKB_MORPH_FACTORY_BODY_V1" || magic || version || kind || flags || body_len || body_bytes)` differs from the implementation's `blake2b256([CKB_MORPH_WITNESS_ENVELOPE_BODY, kind_le, body])`.
**Evidence**:
- Paper: `body_commitment = \hash(...)` at `paper.tex:1835-1843` includes `magic, version, kind, flags, body_len, body_bytes` and the domain `CKB_MORPH_FACTORY_BODY_V1`.
- Rust: `blake2b256(&[WITNESS_ENVELOPE_BODY_DOMAIN, &kind.to_le_bytes(), body])` at `morph-script-common/src/lib.rs:427-429`; `WITNESS_ENVELOPE_BODY_DOMAIN = b"CKB_MORPH_WITNESS_ENVELOPE_BODY"` at `lib.rs:141`. Magic/version/flags/body_len are not included in the body commitment.
**Impact**: The body commitment is *checked* against the envelope's pinned `magic, version, flags, body_len` (the envelope's header fields are fixed-width and the body is bound to its length). A different `magic, version, flags, body_len` would produce a different `kind` lookup failure or a different length-allowed check (`lib.rs:448-471`). So the safety is preserved in practice, but the paper's formula is not literally implemented.
**Suggested fix**: paper — replace the explicit `magic || version || kind || flags || body_len || body_bytes` with `H(domain, kind, body)` and note that the envelope's header fields are pinned by the parse rule, not by the body commitment. Code — document this in `compute_body_commitment`.

### W2-09 — `descriptor.max_outputs` in FUND_BOUNDS is unfixed in code (MEDIUM)
**Severity**: MEDIUM (already flagged as S2 in prior audit; not yet applied)

## Cross-cutting

1. **The audit-response doc and the patch doc together close 12 of 13 high/medium findings from the audit-response** (C-01, H-01..H-07, M-01..M-04). The bilateral profile is therefore in a defensible state on the *implementation* side. The right-kind encoding (5 types, 0..=4) matches the paper's `FactoryRight` set (paper 1908-1911).
